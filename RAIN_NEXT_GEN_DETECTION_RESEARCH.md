# Rain Anti-Cheat: next-generation detection research

**Research snapshot:** 27 September 2026. **Scope:** static source review and engineering design only. No cheat binaries were run; no Rain detection code was changed. This report describes the *working tree* of Rain, including pre-existing uncommitted work, rather than an assumed released build.

## 1. Executive summary

Rain's central problem is **identifiability**, not a shortage of thresholds. It observes a server's rebroadcast, interpolated representation of other players. Several materially different causes—human play, a modified client, network jitter, server policy, and plugin behavior—can produce the same observations. In the present build Rain has three tick-polled checks (KillAura, AutoBlock, LegitScaffold) and a first-flag-wins mark. It has no remote player's raw mouse input, outgoing packets, exact attack intent, or known server-authoritative hit validation. A high-accuracy version must say **insufficient evidence** for most subtle AimAssist, AutoClicker, WTap, partial Velocity, and low-amplitude Reach cases.

The highest-value next step is an **observation and attribution layer**, not more named cheat checks. Record what was actually observed, at what resolution, under which lag/visibility conditions; represent possible attacker–victim and placement episodes with explicit uncertainty; retain short evidence transcripts; then evaluate a small set of specialized hypotheses. Add a passive **incoming** packet tap only if the injected runtime can support it safely. That can recover server-to-observer entity-look, animation, metadata, status, and block-change timing, but it still cannot reveal the suspect's serverbound attack, placement, or movement packets. If that tap is unavailable, keep those detectors in research/shadow mode or omit them.

**Priority order:** (1) visibility and quality instrumentation; (2) correct event attribution and replayable evidence; (3) conservative reach/line-of-sight envelopes for exceptionally clear fights; (4) combat rotation episodes and multi-target geometry as supporting evidence; (5) entity-local lag correlations, knockback and placement hypotheses with strict prerequisites; (6) dataset and only then ML. Do not display a numerical “cheat probability” without calibration on independent players, servers, and cheat settings. A score is an internal evidence index until validated.

**Important adversarial result:** Raven's closet modules deliberately humanize or condition behavior. Its Aura caps rotation per update and quantizes to the mouse-sensitivity step; LeftClicker uses randomized timing and pauses; Reach can act only while moving/sprinting/holding a weapon. NightX can choose no rotations, no swing, fake visual blocking, partial velocity, packet buffering, and path-based InfiniteReach. A detector relying on one stereotyped signature will miss configurations and falsely accuse edge cases.

## 2. Method, provenance, and epistemic labels

The external repositories were cloned for **reading only** at these commits: [Raven `5f18282`](https://github.com/K-ov/Raven/tree/5f18282e78418a99ac4167fde3e90c49fa2487b5), [NightX `1c77144`](https://github.com/Aspw-w/NightX-Client/tree/1c771444a9120d8c06fe7d88a3f5849402849bb4), [Iustitia `9cf356f`](https://github.com/ThoriaDevelopment/Iustitia/tree/9cf356fe9a537d3caa7836d5f0936f70deba0de1), [Grim `8eb5f28`](https://github.com/GrimAnticheat/Grim/tree/8eb5f2809591c891deb4958bb2927844871e0600), [Lumo `9a6de02`](https://github.com/isLumo/LumoAiDetector/tree/9a6de02c702eaf87b732e0935dc5c387751ddeea), [Shard `4118112`](https://github.com/KaelusAI/Shard/tree/41181121fd563b36427116422185301f76b6dcf4), and [AimNet `0b5d581`](https://github.com/templateprotection/AimNet-Mouse-Dynamics/tree/0b5d5817195b4551d364b4ca28f8e510a867a82b). File links below pin that code where possible. Source shows **intended mechanisms**, not evidence that a mode works on a particular server. Some modules contain questionable or incomplete logic; do not assume every advertised bypass succeeds.

This report uses four labels:

* **Direct:** available in Rain's current runtime from the remote `EntityPlayer` or local world snapshot.
* **Inferred:** a hypothesis about an event or cause built from direct data; retain alternatives.
* **Unavailable:** information the current observer does not receive. An incoming packet tap may improve timing, but never grants the suspect's serverbound stream.
* **Conditional:** available only on servers/versions that rebroadcast it, after an explicitly scoped future passive tap, or when the observer is personally involved.

“Definitive” should mean the *observation itself* is physically incompatible with every allowed legitimate trajectory under stated uncertainty. A client-sided observer should rarely use this label. Repeated, striking geometry may be **strong evidence**, but server plugins, hidden knockback policy, and incomplete attack attribution defeat an absolute claim. “Supporting” evidence belongs in a transcript; “too ambiguous” should be logged for study, not sent as an accusation.

## 3. Rain today: architecture and observation limits

### 3.1 Execution and state map

The Forge/injected shared tick entry at [`Rain.java`](runtime/src/first/rain/anticheat/Rain.java) handles `ClientTickEvent.END`, clears on world change, walks loaded `playerEntities`, retains UUID state, and invokes checks in combat–AutoBlock–Scaffold order. [`AntiCheatData.java`](runtime/src/first/rain/anticheat/util/anticheat/AntiCheatData.java) owns the three check instances and their lifecycle. There is no input-packet listener in this path. The project targets a 1.8.9-style Minecraft/Forge runtime; modern 1.21 examples are conceptual comparisons, not drop-in protocol logic.

[`PlayerEligibility.java`](runtime/src/first/rain/anticheat/util/anticheat/PlayerEligibility.java) excludes dead/spectator entities and requires a UUID/name match in the tab-list network info. This reduces NPC contamination but is not proof of humanness: server-backed bots or plugins can satisfy it. It also removes data on temporary unload/despawn and resets marked state for players no longer loaded. An excluded player is **unobserved**, never verified legitimate.

[`KillauraCheck.java`](runtime/src/first/rain/anticheat/util/anticheat/checks/KillauraCheck.java) keeps UUID state and five-tick position trails. It notices the **edge of the local swing animation boolean**, scans nearby real players, and treats a victim `hurtTime` rise near the swing, within 4.5 blocks, within an 18° approximate aim box, and line of sight as likely combat. This is an attribution heuristic. It then analyzes yaw bursts and unusually sustained target tracking in a twenty-tick combat window; [`AimGeometry.java`](runtime/src/first/rain/anticheat/util/anticheat/checks/AimGeometry.java) computes angular error to an approximate body box. [`AimEvidence.java`](runtime/src/first/rain/anticheat/util/anticheat/checks/AimEvidence.java) needs score ≥220, both snap/return and track source groups, and three inferred hits. This is useful independence within *aim mechanics*, but the shared inferred-hit gate can still be wrong. The magic weights and 0.85 tracking ratio are uncalibrated; an “80” component is not 80% certainty.

[`AutoBlockCheck.java`](runtime/src/first/rain/anticheat/util/anticheat/checks/AutoBlockCheck.java) consumes Killaura's `hasRecentCombat`. [`AutoBlockEvidence.java`](runtime/src/first/rain/anticheat/util/anticheat/checks/AutoBlockEvidence.java) counts edge-like swing/block overlaps after a sustained block run, with a short late-hurt allowance. Crucial weakness: it inherits the same attack attribution error; the two alerts are not independent corroborators. Legitimate block-hitting and animation overlap are plausible. NightX's default **Fake** AutoBlock only changes local visuals and may leave no remote blocking state at all.

[`LegitScaffoldCheck.java`](runtime/src/first/rain/anticheat/util/anticheat/checks/LegitScaffoldCheck.java) treats held block, ground, downward pitch ≥60°, and bridge-like displacement as context. [`ScaffoldEvidence.java`](runtime/src/first/rain/anticheat/util/anticheat/checks/ScaffoldEvidence.java) counts 1–2 tick crouches with repeated duration and a nearby swing; [`EpisodeEvidence.java`](runtime/src/first/rain/anticheat/util/anticheat/checks/EpisodeEvidence.java) decays a small tick score and requires several episodes. No actual placed block, face, support geometry, or cursor is currently attributed. This is a **rhythmic crouch while bridging** detector, not a verified Scaffold detector. NightX LegitScaffold can auto-sneak and right-click at an edge, but human eagle bridging creates much the same pattern.

[`AlertManager.java`](runtime/src/first/rain/anticheat/util/anticheat/AlertManager.java) marks once per UUID and displays “flagged [module] (VL: n).” Subsequent detections are hidden except periodic debug logging. The first winning check fixes the public label; there is no transcript, contradiction, quality score, uncertainty interval, evidence diversity, or calibrated confidence. Marking is erased on world change or when a player leaves the loaded set. A colored nametag or flash makes the uncalibrated first verdict highly salient.

### 3.2 What the current observer can and cannot know

| Question | Current Rain | Why it matters |
|---|---|---|
| Remote position, yaw/pitch, selected item, sneak/sprint/use state, animation, hurt timer, nearby blocks | **Direct snapshot** if entity is loaded and server exposes state | A tick poll sees *the client's interpolated presentation*, not the exact server event sequence. Metadata and custom servers can alter semantics. |
| Remote movement speed, yaw change, target bearing, block support, line of sight | **Derived from snapshots** | Requires sampling cadence, interpolation, collision, and position/rotation uncertainty. A single tick is weak. |
| “A attacked B at tick t” | **Inferred** from swing/hurt/proximity | Hurt can be environmental, projectile, another attacker, or delayed; swing can be digging/miss. Crowded fights need explicit ambiguity. |
| Remote clicks and CPS | **Unavailable** | At best a subset of server-relayed swings. Misses, unsent animation, local click timing, multi-click within a tick, and server suppression are lost. |
| Remote serverbound C02 attack, C03 movement/look, C08 placement, C0B sprint, C0F transaction, C00 keepalive | **Unavailable** | The observer is neither suspect nor server. Do not turn these into “packet checks” in Rain. |
| Actual server-side hit result, damage cause, velocity impulse, item-use slowdown, TPS, suspect ping | **Conditional/usually inferred** | Tab ping is at best server-reported RTT and not a synchronized one-way latency to the suspect; damage/velocity rebroadcast varies. |
| Opponent's camera aim, raw mouse deltas, sensitivity/DPI/FPS, key presses, local fake visuals | **Fundamentally unavailable** | A remote head/body rotation is not mouse motion. Cannot identify GCD/mouse hardware directly. |
| Incoming rebroadcast packet class and arrival time | **Not captured today; conditional future capability** | A passive read-only hook can improve event timing/quality and preserve raw quantized look. It cannot manufacture source packets. |

In 1.8.x the rebroadcast entity-look yaw/pitch are byte-angle values (360/256 = **1.40625°** per step), while client presentation interpolates toward them. See the [1.8 protocol description](https://github.com/pdelvo/McDevsWiki/blob/master/Protocol.md) and Rain's own `QUANTUM` comment. Differencing interpolated rotations and then differentiating again creates apparent acceleration and jerk that the suspect never sent. Even an incoming packet tap does **not** recover fine-grained mouse sensitivity: it only gets quantized server output. A GCD detector trained on raw serverbound float rotations cannot be transferred to Rain's tick-polled remote entity.

### 3.3 Existing checks: specific failure and strength audit

| Current check/state | What is already sensible | Failure mode to measure before widening it |
|---|---|---|
| KillAura combat gate | Requires several hurt-correlated, aim-plausible events rather than any turn near a player; retains short victim trails; rejects riding and large moves. | `hurtTime` rising is not an attacker ID. In a two-attacker melee both can have recent swings and appear aimed at one hurt victim. The five-position victim trail is not a synchronized history of *both* participants. `canEntityBeSeen` at evaluation time need not match line of sight at the hit instant. |
| Snap/return component | Requires a burst to settle into a recent combat target and tests pre-burst angular error; return shares its source group. | Thresholds such as 7° step, 20° sum and 1.40625° hitbox error have no measured legitimate distribution. A human flick can settle inside the broad target box; tick interpolation shapes a single network rotation into multiple steps. `pitch` is evaluated at current tick while `preBurstYaw` refers to an earlier tick. |
| Tracking component | Restricts to a moving target at ≥2.2 blocks, uses 24 eligible samples and 85% inside-box ratio. | The source comment “humans drift” is a hypothesis, not a measured null. Good tracking during a short strafe may satisfy it. Samples within one continuous fight are highly correlated; they are not 24 independent pieces of evidence. Five-frame target trails make an inside-box result *easier* to satisfy. |
| AimEvidence fusion | Requires two source groups and at least three combat events; decays and resets. | Snap and tracking share target selection, rotation stream and the same inferred-hurt gate. `sourceMask==3` does not establish independent modalities. Score/VL units lack probability or false-positive calibration. |
| AutoBlock | Counts episodes instead of each overlapping animation tick; permits late hurt correlation. | It calls Killaura's `hasRecentCombat`, so an attribution error contaminates both checks. A legitimate sword block-hit can overlap swing and use state; NightX Fake mode may produce no remote block state. |
| LegitScaffold | Requires several regular short crouches while holding blocks, grounded and looking down. | No placed-block observation is attached to the player. A regular human eagle bridge or assisted bridging produces the same conditions. `field_82175_bq` is animation state, not a confirmed placement. Its current public name overstates the measurement. |
| AlertManager/eligibility | Filters obvious nonplayers and avoids repeated chat/flash spam. | First flag permanently owns the label for the loaded session; no later contradiction or better evidence can correct it. Tab-list presence is not proof of a human player, and removing unloaded players discards history. Public “flagged” wording is stronger than the present evidence warrants. |

This audit does **not** assert that the present checks have a measured false-positive rate; no such validation was found in the reviewed runtime. Their current guards are worth preserving as candidate quality features, but a research blueprint cannot promote their scores into confidence percentages.

## 4. Raven deep dive: closet behavior and real code

The source paths in this section start with `src/main/java/keystrokesmod/client/` in the pinned Raven commit.

### 4.1 Combat aim, attacks, and reach

**AimAssist** ([`AimAssist.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/combat/AimAssist.java#L27-L129)) runs in `RenderWorldLastEvent`, chooses the first non-bot/non-friend player inside configurable FOV and distance, and optionally requires a held weapon and **physical left mouse button**. It stops while breaking blocks. It changes local yaw by a fraction of target angular error with randomized speed terms, and pitch only when enabled. `blatantMode` calls a direct aim helper. This is genuine humanization: visible turns can be small, irregular, conditional, and mixed with the user's own input. Rain might see better-than-expected error reduction during fights, but cannot know the target choice or mouse movement. Against this module, measure *episodes of conditional target-error convergence* with negative controls (noncombat turns and plausible alternative targets), not a universal smoothness or GCD rule. Skilled tracking, a crossing target, or low FPS can look similar.

**KillAura** ([`aura/KillAura.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/combat/aura/KillAura.java#L58-L244)) selects by distance/health/armor within FOV and reach, optionally requires mouse down and survival mode, and disables on flying/teleport conditions. It caps turn per game-loop update (`maxRps/2`), then floors yaw/pitch to a local sensitivity-derived `f³ × 1.2` step. Its “GCD Fix” is exactly why invalid-GCD heuristics are brittle. It draws randomized CPS from a range and adds jitter to attack delay. Optional block ray tracing swings but skips attack behind a block. Attack execution unblocks, swings, attacks, then uses Spoof/Interact/BlockHit modes. It writes event yaw/pitch and adjusts movement input to the new yaw while generally leaving the local camera unsnapped. **Observable residue** may be target switching, rotation landing, a packet-level aim/attack mismatch, or hit geometry; each can disappear with settings and is degraded by remote quantization. Movement correction specifically weakens a “movement bearing versus head yaw” rule.

**LegitAura2** ([`LegitAura2.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/combat/LegitAura2.java#L47-L240)) is not simply the main aura renamed. It requires mouse down by default, has narrow FOV, sorts by distance/hurt time/FOV, sends target rotations in `UpdateEvent`, and injects keybind clicks. Its delay generator occasionally stretches bursts or adds a 50–150 ms pause. An otherwise regular click process can therefore have low-level burstiness similar to manual clicking. A remote observer sees only relayed swing subset, making strong AutoClicker claims untenable without richer evidence.

**Reach** ([`Reach.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/combat/Reach.java)) randomizes within 3.1–3.3 blocks by default, can require weapon/movement/sprint, and modifies local entity selection in [`MixinEntityRenderer.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/mixin/mixins/MixinEntityRenderer.java#L60-L112). The default excess is smaller than realistic passive-observer uncertainty in many fights. Very clear stationary, isolated, repeated over-distance hits are the appropriate research target. “3.3 observed once” is **not** evidence of cheating for Rain.

**HitBoxes** ([`HitBox.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/combat/HitBox.java#L20-L60)) adds a local raycast-box expansion used by the same renderer mixin. The server does not broadcast that local expanded box. Only a resulting suspected hit outside every plausible standard hitbox/latency envelope could support a claim; merely seeing wide aim error or normal hits cannot identify it.

**LeftClicker** ([`LeftClicker.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/combat/LeftClicker.java#L65-L323)) requires mouse held, may restrict weapon or block breaking, chooses Render or Tick timing, randomizes CPS/hold lengths, occasionally delays, and optionally jitters yaw/pitch. It can operate through Minecraft click handling/keybinds. Thus remote animation timestamps are a censored, server-ticked projection of clicks. Exact CPS, entropy, autocorrelation, and variance estimates from Rain's current `isSwingInProgress` edge are not trustworthy. A sustained mechanical pattern might be a **supporting** signal only after a packet-level animation tap and mining exclusions.

### 4.2 Combat movement and defensive modules

**Velocity** ([`Velocity.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/combat/Velocity.java)) multiplies local X/Z and Y motion when hurt starts; default horizontal 90%, vertical 100%. It can act by chance, only while targeting, not while S is held, and use projectile-specific scaling. A ten-percent horizontal reduction is usually below Rain's recoverable precision without known impulse and movement controls. Treat “didn't move enough after hurt” as **ambiguous** unless an impulse is actually rebroadcast or the observer can bound pre-hit momentum, wall collision, surface, jump, and latency. Even then use repeated clean cases.

**WTap/STap/ShiftTap** ([`WTap.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/combat/WTap.java), [`STap.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/combat/STap.java)) key-toggle movement near an attack or hurt with randomized action/hold delays and chance/hit-count gates. Rain may see transient sprint/sneak state or displacement, but manual combo techniques are normal PvP. A WTap detector is not a useful standalone flag; at most it can contextualize combat motion. **KeepSprint** ([`KeepSprint.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/movement/KeepSprint.java), called from `MixinEntityPlayer`) changes local post-hit slowdown and can still explicitly stop sprinting. Do not equate continued sprint state with this cheat. **NoSlow** ([`NoSlow.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/movement/NoSlow.java), actual slowdown in [`MixinEntityPlayerSP.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/mixin/mixins/MixinEntityPlayerSP.java#L231-L251)) replaces vanilla `0.2` movement input factor during item use with `(100 - Slow%)/100`; default Slow% 80 means vanilla. It optionally cancels local inventory reset packets. Rain would need reliable *remote item-use state*, clean ground/surface, and a physical movement envelope before even studying NoSlow; the default has no speed anomaly.

**Criticals** ([`Criticals.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/combat/Criticals.java)) sends four small position/ground-state packets before attack in Packet mode, or jumps in Jump mode. The passive observer will generally not see the packets' ground bits or sub-tick offsets; a genuine jump is indistinguishable. Critical-hit particle/damage interpretation is server-specific. **Backtrack** ([`Backtrack.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/combat/Backtrack.java)) caches target positions and queues selected outgoing C03s for delayed resend. *This implementation's shown `onPacketSend` does not cancel the original packet*, so its real delay effect needs verification; do not label all of its behavior as proven. If a separate mode yields local freeze/catch-up, an observer may see that, but network jitter creates the same silhouette.

### 4.3 Bridging, timing, and lag

**Scaffold/ScaffoldPlus** ([`Scaffold.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/world/Scaffold.java), [`ScaffoldPlus.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/world/ScaffoldPlus.java)) search support blocks, set placement rotations in update/look events, invoke client placement, and can swing. Plus adds tower, KeepY, SafeWalk/Eagle, sprint control, delay, extension, and rotation modes including backward/none. The most informative *observable* residue would be a sequence of confirmed blocks at edge positions plus rotation/face geometry, not sneak rhythm. A silent placement rotation might be packet-visible but visually hidden to the cheater; Rain gets only server-relayed orientation. **BridgeAssist/SafeWalk** ([`BridgeAssist.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/player/BridgeAssist.java), [`SafeWalk.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/player/SafeWalk.java)) can glide aim and time short shifts near edges. That directly attacks Rain's current LegitScaffold rationale: legitimate human eagle bridging and assist timing may overlap in the observations.

**FastPlace** ([`FastPlace.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/player/FastPlace.java)) reduces the client's right-click delay timer, optionally for blocks or projectiles. **FastBreak** ([`FastBreak.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/player/FastBreak.java)) has instant, repeated-dig-packet, timer, switch, and hybrid paths. Rain's current tick check has neither exact remote placement nor dig progress; block changes are shared world events and attribution is hard. Server plugin mining/placement rules can legitimately change cadence.

**Blink/FakeLag** ([`player/Blink.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/player/Blink.java), [`other/FakeLag.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/other/FakeLag.java)) queue selected outgoing packets, with movement/combat/smart or normal/burst/smooth releases and optional action conditions. The visible signature is at best entity-local silence followed by server updates, ideally correlated with combat while other entities continue. That is **supporting**, not a cheat verdict: selective entity tracking, chunk boundaries, server scheduling, and an individual's bad connection create false matches. **Disabler** ([`other/Disabler.java`](https://github.com/K-ov/Raven/blob/5f18282e78418a99ac4167fde3e90c49fa2487b5/src/main/java/keystrokesmod/client/module/modules/other/Disabler.java)) changes/cancels specific outgoing packets by mode. The observer cannot inspect those packets; only downstream movement/placement consequences could be studied. **Timer** changes local `timerSpeed`; Speed/Fly variants alter motion. Rate alone cannot prove Timer without a synchronized source tick stream and server-policy model.

## 5. NightX deep dive: aggressive packet and movement adversary

NightX paths start with `src/main/java/net/aspw/client/` at pinned commit `1c77144`.

**KillAura** ([`KillAura.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/combat/KillAura.kt#L50-L214), [attack/rotation code](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/combat/KillAura.kt#L461-L786)) separates target range from attack range; chooses priority and Single/Switch/Multi; randomizes CPS, turn speed, and fail rate; optionally checks walls; and supports Standard/Zero/None rotations and `NoHitCheck`. Standard limits change toward a bounding-box point; Zero chooses a nearest point; `roundRotation` alters yaw. It can inject attacks before or after swing, use packet/smart/no-swing modes, raycast to a different actually hit entity, and use multiple autoblock modes. Multi attacks several entities in one internal cycle. **Rain consequences:** multi-target hurt/swing geometry over a short window can be strong if victims are disjoint and attribution is unambiguous, but a single swing/hurt pattern is not a reliable click or target count. “None” rotation destroys a rotation-based detector. `FailRate` deliberately adds misses. `Fake` blocking produces a local visual effect; Rain's AutoBlock must not expect a remote block marker. `AntiBlink`, inventory and sprint conditions reduce coverage. [`KillAuraRecode.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/combat/KillAuraRecode.kt) uses another face-look/attack loop, a useful held-out cheat family rather than a mere configuration of one function.

**AutoClicker/TriggerBot** ([`AutoClicker.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/combat/AutoClicker.kt), [`TriggerBot.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/combat/TriggerBot.kt)) drive keybind clicks at randomized min/max CPS; TriggerBot fires only while `objectMouseOver` selects a target and can wait for the cooldown. The result can resemble good target discipline. Rain currently cannot count all clicks; at most it can examine **relayed swing-to-target entry coupling**, after excluding mining and censoring gaps.

**AntiVelocity** ([`AntiVelocity.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/combat/AntiVelocity.kt)) contains full cancel, horizontal/vertical packet scaling, chance gating, reverse, jump/strafe, and server-named modes. The direct evidence is in the cheater's handling of `S12` and `S27`, which Rain does **not** see. A measured motion response is only a weak proxy unless impulse and environment are constrained. **LegitVelocity** ([`LegitVelocity.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/combat/LegitVelocity.kt)) merely toggles forward/jump keybind states across hurt ticks—behavior a human could replicate. Do not claim to detect it from remote movement alone.

**BackTrack** ([`BackTrack.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/combat/BackTrack.kt)) delays selected *incoming* entity move/teleport packets locally and flushes on attack or reset conditions. This is a critical distinction: other observers receive ordinary server broadcasts and may see **nothing distinctive**. It can let the cheater interact with a stale local target, but only a server-visible hit outcome plus trusted timing could expose that, and server lag compensation might allow it legitimately. **InfiniteReach** ([`InfiniteReach.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/other/InfiniteReach.kt)) does not simply send a distant attack. It computes a path, emits position packets to the target, performs attack/dig/place, and emits the reverse path. A remote observer may see a rapid excursion or no coherent intermediate path, depending on server acceptance and broadcast coalescing. Therefore detect **possible impossible travel + interaction** under clean observations, not “long reach” measured from a stale pre-path location. Reject server teleports, rubber-banding, and packet-burst ambiguity.

**Scaffold/LegitScaffold/Tower** ([`Scaffold.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/player/Scaffold.kt), [`LegitScaffold.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/player/LegitScaffold.kt)) choose placement neighbors/face/hit vectors, use target rotations and smooth/normal modes, choose randomized placement delay, SafeWalk and tower motion modes. LegitScaffold auto-sneaks at an air edge, keybind-right-clicks, stops sprint, and limits rotation toward a near-80° pitch with randomized speed. A passive observer can potentially connect a block change to a nearby holder and inspect angle to plausible faces, but **never sees the C08 face or cursor**. A block change alone could come from another player or plugin. The current repeated-crouch check should be demoted until placement attribution is available.

**Blink/FakeLag/PingSpoofer/Disabler** ([`Blink.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/player/Blink.kt), [`FakeLag.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/exploit/FakeLag.kt), [`PingSpoofer.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/exploit/PingSpoofer.kt), [`Disabler.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/exploit/Disabler.kt)) buffer/cancel different packet classes or delay keepalive/status. Blink queues movement plus optional action/transaction packets and flushes by pulse. FakeLag has inbound/outbound/all with random delays; inbound buffering can change only the cheater's local view, while outbound movement buffering may create freezes/bursts for Rain. PingSpoofer delays the suspect's keepalive; Rain does not receive those packets or a trustworthy per-event RTT. Disabler mode names are not remote observables. Treat packet-gap/combat correlation as a supporting axis with a global-lag negative control.

**Criticals, WTap, KeepSprint, NoSlow, Timer, Speed, Flight** ([`Criticals.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/combat/Criticals.kt), [`WTap.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/combat/WTap.kt), [`KeepSprint.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/combat/KeepSprint.kt), [`NoSlow.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/movement/NoSlow.kt), [`Timer.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/player/Timer.kt), [`Speed.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/movement/Speed.kt), [`Flight.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/movement/Flight.kt)) include ground/position spoof, packet-timed bursts, explicit sprint-action toggles, use-item movement manipulation, and many named movement profiles. `KeepSprint.kt` itself is a marker module whose effect must be traced through other code; its empty class is **not** proof of a particular motion signature. NightX WTap's “Legit” mode actually toggles sprint state across updates; “FakeSneak” emits actions, many of which may not be visible in a one-tick poll. Generic speed/flight bounds need calibrated terrain, potion, server and protocol assumptions; mode-specific magic constants are not portable.

**SilentRotations** ([`SilentRotations.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/features/module/impl/visual/SilentRotations.kt), [`RotationUtils.kt`](https://github.com/Aspw-w/NightX-Client/blob/1c771444a9120d8c06fe7d88a3f5849402849bb4/src/main/java/net/aspw/client/utils/RotationUtils.kt)) separates camera and server rotation and may correct strafing. Rain sees the rebroadcast server-facing representation if the server sends it, **not** the cheater's camera. A “silent rotation” cannot be named confidently from a single remote stream. NightX `HitBox.kt` and `FastPlace.kt` are settings holders whose actual effect is elsewhere; inspect call sites before proposing a signature.

This matrix groups mechanisms by the **observable residue**, not by module marketing name. “Now” means the present Rain tick poll. “Tap” means a *future* read-only **incoming** packet observer with server-specific coverage checks. Every proposed signal requires the quality gates in §9–10. None implies Rain sees a serverbound cheat packet.

## 7. External anti-cheat and data research: lessons and transfer limits

### 7.1 Iustitia: closest architectural peer

[Iustitia](https://github.com/ThoriaDevelopment/Iustitia) is genuinely client-sided and passive, but its read-only [`ClientPlayNetworkHandlerMixin.kt`](https://github.com/ThoriaDevelopment/Iustitia/blob/9cf356fe9a537d3caa7836d5f0936f70deba0de1/src/main/kotlin/dev/iustitia/mixin/ClientPlayNetworkHandlerMixin.kt) records incoming animation, damage, velocity and other signals. Rain's tick-only layer is **less informed**. [`AttackInference.kt`](https://github.com/ThoriaDevelopment/Iustitia/blob/9cf356fe9a537d3caa7836d5f0936f70deba0de1/src/main/kotlin/dev/iustitia/inference/AttackInference.kt) explicitly joins observed hurt, swing and candidate actors; the join remains an inference, which Rain should preserve in an evidence record. [`ReachCheck.kt`](https://github.com/ThoriaDevelopment/Iustitia/blob/9cf356fe9a537d3caa7836d5f0936f70deba0de1/src/main/kotlin/dev/iustitia/checks/combat/ReachCheck.kt) tests attacker/victim history, hitbox intersection and a generous fallback headroom; its source explicitly acknowledges that client-sided reach has poorer resolution than server checks and focuses on blatant cases. Its [`ClickStatisticsCheck.kt`](https://github.com/ThoriaDevelopment/Iustitia/blob/9cf356fe9a537d3caa7836d5f0936f70deba0de1/src/main/kotlin/dev/iustitia/checks/combat/ClickStatisticsCheck.kt) excludes mining relay cadence and same-tick batches from some statistics, a valuable warning against naive CPS. [`NoKnockbackCheck.kt`](https://github.com/ThoriaDevelopment/Iustitia/blob/9cf356fe9a537d3caa7836d5f0936f70deba0de1/src/main/kotlin/dev/iustitia/checks/combat/NoKnockbackCheck.kt) explicitly handles walls, dampening surfaces and missing rebroadcast velocity.

Useful transfer: event provenance, short position rings, lag windows, negative controls, per-check evidence payloads ([`Evidence.kt`](https://github.com/ThoriaDevelopment/Iustitia/blob/9cf356fe9a537d3caa7836d5f0936f70deba0de1/src/main/kotlin/dev/iustitia/history/Evidence.kt)), transcript/clip replay, and testing both cheat and legitimate scenarios. [`LagCombatCorrelator.kt`](https://github.com/ThoriaDevelopment/Iustitia/blob/9cf356fe9a537d3caa7836d5f0936f70deba0de1/src/main/kotlin/dev/iustitia/tracking/LagCombatCorrelator.kt) compares a suspect-local freeze with global lag and combat timing—a **correlation amplifier**, not proof. [`FlagHistory.kt`](https://github.com/ThoriaDevelopment/Iustitia/blob/9cf356fe9a537d3caa7836d5f0936f70deba0de1/src/main/kotlin/dev/iustitia/history/FlagHistory.kt) distinguishes primary and corroborating checks and decays public tiers.

Challenge: the Iustitia source calls some checks “definitive” and maps history to a 0–99 confidence score/“≥95%” display concept. A hand-coded tier is **not a calibrated probability**; Rain should not inherit that language without empirical calibration. Likewise, its reach headroom and version-specific attack packet/weapon assumptions cannot be copied into 1.8.9. Its packet tap still does not see suspect outbound attack packets. [Iustitia's automated live testing](https://thoriadevelopment.github.io/Iustitia/docs/automated-live-testing.html) is a useful model for regression design, although Rain must test its own injected/Forge observer and server mix.

### 7.2 Grim: model physical possibility, retain uncertainty

[Grim's Reach](https://github.com/GrimAnticheat/Grim/blob/8eb5f2809591c891deb4958bb2927844871e0600/common/src/main/java/ac/grim/grimac/checks/impl/combat/Reach.java), [`ReachInterpolationData`](https://github.com/GrimAnticheat/Grim/blob/8eb5f2809591c891deb4958bb2927844871e0600/common/src/main/java/ac/grim/grimac/utils/data/ReachInterpolationData.java), [`PredictionRunner`](https://github.com/GrimAnticheat/Grim/blob/8eb5f2809591c891deb4958bb2927844871e0600/common/src/main/java/ac/grim/grimac/checks/impl/movement/PredictionRunner.java), and [`UncertaintyHandler`](https://github.com/GrimAnticheat/Grim/blob/8eb5f2809591c891deb4958bb2927844871e0600/common/src/main/java/ac/grim/grimac/predictionengine/UncertaintyHandler.java) illustrate testing a set of plausible player/world trajectories rather than one scalar threshold. Its [`KnockbackHandler`](https://github.com/GrimAnticheat/Grim/blob/8eb5f2809591c891deb4958bb2927844871e0600/common/src/main/java/ac/grim/grimac/checks/impl/velocity/KnockbackHandler.java), [`NoSlow`](https://github.com/GrimAnticheat/Grim/blob/8eb5f2809591c891deb4958bb2927844871e0600/common/src/main/java/ac/grim/grimac/checks/impl/movement/NoSlow.java), and [placement checks](https://github.com/GrimAnticheat/Grim/tree/8eb5f2809591c891deb4958bb2927844871e0600/common/src/main/java/ac/grim/grimac/checks/impl/scaffolding) have access to serverbound actions, versioned collision rules, and server-timed state Rain lacks. Transfer **the philosophy and uncertainty accounting**, not numeric limits or packet dependencies. Rain should ask: “Does *any* allowed trajectory fit?” If yes, abstain. If the allowed set cannot be bounded from passive data, that detector is not ready.

### 7.3 LumoAiDetector: interpretable pilot, leakage warning

[Lumo's `DetectionService.java`](https://github.com/isLumo/LumoAiDetector/blob/9a6de02c702eaf87b732e0935dc5c387751ddeea/src/main/java/com/lumskyy/lumoaidetector/detector/DetectionService.java#L165-L207) makes 15-sample combat-gated windows with yaw/pitch steps, `dt`, angular speed, absolute acceleration/jerk, nearest-target error and error derivative. It rejects absent targets, low motion, long gaps and unstable timing. Its [`ModelService.java`](https://github.com/isLumo/LumoAiDetector/blob/9a6de02c702eaf87b732e0935dc5c387751ddeea/src/main/java/com/lumskyy/lumoaidetector/ml/ModelService.java#L190-L379) trains a local Smile Random Forest, balances classes and reports held-out metrics. Transfer the **data-quality gate, small interpretable feature window, and recording workflow**. Two cautions: Lumo is a **server plugin** using player move/attack events, so Rain's remote deltas are coarser; and the reviewed split shuffles *rows* within class, not sessions/players. Neighboring sliding windows from one fight can land in train and validation, yielding optimistic metrics. A Rain evaluation must group by person/session and ideally by server and cheat implementation.

### 7.4 Shard: production sequence plumbing, not a public model recipe

[Shard `AiCheck.kt`](https://github.com/KaelusAI/Shard/blob/41181121fd563b36427116422185301f76b6dcf4/src/main/kotlin/ac/shard/checks/impl/ai/AiCheck.kt) collects serverbound flying-packet yaw/pitch deltas into a [`TickRingBuffer`](https://github.com/KaelusAI/Shard/blob/41181121fd563b36427116422185301f76b6dcf4/src/main/kotlin/ac/shard/checks/impl/ai/TickRingBuffer.kt), filters duplicate/riding/noncombat cases, and submits windows to a remote inference API. It increments/decrements a buffer based on returned model probabilities; [`DataCollectorCheck.kt`](https://github.com/KaelusAI/Shard/blob/41181121fd563b36427116422185301f76b6dcf4/src/main/kotlin/ac/shard/checks/impl/ai/DataCollectorCheck.kt) records labeled server sessions. The public plugin code supports *sequence collection, backpressure, resets, and temporal buffering*. It does **not** expose enough model architecture/training data to establish accuracy or transfer its `>0.9` threshold. Shard's two deltas per serverbound tick are not Rain's interpolated byte-angle deltas. Rain should be local-first: no cloud inference or account linkage is warranted by evidence here.

### 7.5 AimNet and additional academic work

[AimNet's README](https://github.com/templateprotection/AimNet-Mouse-Dynamics/blob/0b5d5817195b4551d364b4ca28f8e510a867a82b/README.md) describes 2,219 distinct players, anonymized UUID, yaw/pitch deltas, timestamps, absolute rotation, and player/opponent positions. The code uses 100-step LSTM sequences and a triplet/embedding objective for **person identification/continuous authentication**, not cheat-versus-legit classification. Its quoted equal-error-rate examples do not establish cheat detection performance. `AimNet.py` points to `./dataset/aim_data.csv`, but that CSV is **not present in the cloned repository**; verify license, availability, collection consent, timing units, and session boundaries before using it. Its schema is valuable inspiration, especially opponent-relative geometry and player-group evaluation. The data cannot be treated as a ready Rain cheating corpus and its raw/serverbound precision does not match Rain's remote stream.

The [XGuardian paper](https://arxiv.org/abs/2601.18068) discusses generalized and explainable server-side FPS anti-cheat. The transferable lesson is to validate across environments and show human-readable reasons; its game, telemetry, and ground truth differ from Minecraft passive client observation, so none of its reported performance should be imported. [Minecraft's protocol descriptions](https://github.com/pdelvo/McDevsWiki/blob/master/Protocol.md) are more directly useful for defining quantization, entity-update gaps and version-specific visibility. These sources reinforce a methodological point: **match the training and validation stream to the exact deployed observer**, including interpolation and missing packets. A model trained on idealized raw rotations can appear excellent while failing catastrophically on Rain.

## 8. Proposed next-generation architecture

```text
server rebroadcast → provenance-aware observation ledger → quality/visibility gate
                   → candidate event attribution + uncertainty sets
                   → episode features → narrow hypothesis detectors
                   → dependency-aware evidence fusion → abstain/review result
                   → reproducible local transcript
```

**Observation ledger.** For each loaded UUID retain a bounded ring of raw tick snapshot fields, world tick and monotonic local arrival time, source type (`interpolated entity` versus `incoming packet` if added), teleport/spawn/despawn markers, world/dimension, protocol/server profile, and global/local update coverage. Store *missingness*, not fabricated zero movement. If a future tap runs off-thread, copy immutable packet fields and enqueue to the client thread; never mutate or delay packets. Version and server capabilities should be explicit. An observation may be “unknown” even when the entity is visible.

**Attribution graph.** Hurt, swing, block change, motion impulse, and candidate actors are nodes. Edges carry likelihood or at least a bounded plausible time/distance relationship, and every episode records alternatives: e.g., A and C both could have hit B, environmental damage possible, unknown projectile. If actor identity is ambiguous, geometry checks requiring a specific attacker abstain. Do not use the Killaura check's conclusion as an independent fact for AutoBlock or knockback.

**Physical envelopes.** Represent attacker and victim positions as sets over allowed recent samples and interpolation/latency slack. For an inferred hit, test the minimum distance between any plausible attacker eye trajectory and any plausible victim box, with appropriate ray occlusion. If **any** physically legal pair exists, there is no impossibility claim. Record the best legal explanation, not just the worst measured distance. Do not silently assume 3.0 reach on creative/custom servers or across protocol versions.

**Quality gate.** Each episode needs a `validity` record: source coverage, elapsed tick continuity, known local FPS gap, teleport/correction, server-wide freeze, crowding, entity load age, world collision confidence, version compatibility, item and game-mode uncertainty. A detector declares required quality fields. On unknown/poor quality it emits `insufficient_evidence(reason)` rather than negative or positive evidence. Absence of suspicious behavior is not exculpatory when the player was unobserved.

**Evidence object and fusion.** A detector returns `hypothesis`, `episode_id`, `severity`, `quality`, `measurement`, `plausible_legit_range`, `alternative_explanations`, `dependencies`, and a short replay span. Fusion is dependency aware: snap, target tracking, and hitbox geometry from the *same* inferred attack are correlated; they may strengthen a narrative but do not count as three independent confirmations. Distinct episodes across time and genuinely different axes (geometry, lag timing, movement) can increase confidence. Decay evidence by **clean exposure**, not merely elapsed world ticks: a player outside tracking range should become stale, not “cleared.”

**Result policy.** Separate `observed anomaly`, `needs review`, and `high-confidence suspicious pattern`. Do not say “Raven,” “NightX,” or even “KillAura” when behavior is compatible with several causes. Public nametag/flash should require a higher, empirically validated threshold than an internal debug transcript; initially ship all new detectors in shadow/review mode. No automatic bans from a passive observer.

## 9. Detector research specifications

The following are hypotheses to validate, **not** approved thresholds. A single check must articulate its null/legitimate alternatives before implementation. Initial mode means present tick snapshots; `tap` is a prerequisite for packet-level features.

### 9.1 Combat attribution and reach envelope — first high-value detector

Require isolated attacker/victim, fresh position history for both, a relayed swing followed by a fresh hurt episode, known game mode/range, no projectile/environment candidate, no teleport/crowding, and sufficient visibility. Approximate eye and victim bounding boxes across a calibrated temporal window. If `d_min` is the smallest possible ray-to-box hit distance after allowing all credible positions, classify only a **large** residual `d_min - legal_reach - calibrated_slack` across repeated independent episodes. This is intentionally conservative; the minimum over alternatives favors the player. Candidate formula:

`r_reach = min_(a∈A, v∈V, τ∈T) rayHitDistance(eye(a,τ), look(a,τ), box(v,τ)) − R_legal(version,mode,item)`

`A`, `V`, and `T` include position/rotation uncertainty and must be bounded by measured observer delay. If no ray intersects, retain a separate `hitbox_miss` diagnostic; it may indicate bad attribution or rotation loss rather than cheat. A future incoming animation/status tap improves event timing but does not supply serverbound C02. Test stationary isolated combat separately from moving combat. **Tier:** potentially strong for gross, repeated outliers; small Raven Reach settings remain undetectable.

### 9.2 Aim trajectory: target-aware, quantization-aware, episode based

Compute wrapped deltas and robust target angular error to the *outside* of every plausible victim box, not a fixed center. Define `e_t = min_valid_targets outsideBoxAngle(yaw_t,pitch_t, box_t)` and `Δe_t = e_t - e_(t−1)`. Analyze attack-adjacent windows versus the same player's comparable noncombat turns, conditioning on target angular speed, distance, occlusion, number of candidate targets and observation quality. Useful features: sustained error reduction, overshoot then correction, reversal rate, normalized tracking residual, switch latency, aim dwell on disjoint targets, yaw/pitch coupling. Use `Δθ_t = wrap(θ_t−θ_(t−1))`; derive angular velocity/acceleration/jerk only across equal, **packet-confirmed** intervals. For tick-interpolated Rain samples, label derivatives as presentation features, not mouse dynamics; quantize uncertainty at least ±one byte angle plus interpolation. No “invalid GCD” standalone flag. Compare an aim episode to a matched human null and require repeated independent combat contexts. **Tier:** supporting for closet aim; strong only with extraordinary multi-target geometry and clean attack attribution.

### 9.3 Multi-target and target-switch geometry

For each inferred attack episode, enumerate all victims with hurt onsets and alternate attackers. Bound the time in which the suspect could aim at each non-overlapping hitbox. A single relayed swing with several victims is potentially informative **only** if the server's damage semantics are known and no sweep/area weapon, explosive, thorns, projectile or overlapping attacker explains it. In 1.8 combat, avoid applying 1.9+ sweep assumptions blindly, but also allow custom server mechanics. Require repeated episodes and preserve victim identities and geometry. **Tier:** strong with strict prerequisites; otherwise supporting/abstain.

### 9.4 Click and TriggerBot statistics — research only until event fidelity improves

The current animation boolean is a duration, not a click counter. With an incoming S0B animation tap, compute interval distributions only for *observed relayed swings*, recording dropped gaps, same-tick batches and mining state. Candidate features include robust interval CV, entropy after tick discretization, short-lag autocorrelation, burstiness, and coupling of swing time to target entering the ray. Model legitimate jitter/butterfly and click-while-mining; do not assert a biological 10 ms law from rebroadcast packets. NightX `Swing=None` and other suppressions make absence uninformative. **Tier:** supporting at best; disable public alerts until a measured low FPR exists.

### 9.5 Entity-local lag and burst correlation

With enough nearby moving peers, compare suspect update gaps to global update gaps. Define a local-gap episode only when the suspect previously moved, had expected tracking coverage, other entities continue updating, and the suspect's stream then catches up. Estimate `P(gap near combat | this player)` versus matched noncombat gaps and same-server peers. Do **not** assume all real lag is global: one player's bad uplink is entity-local. A combat-timed *repeated* pattern plus a geometry anomaly may strengthen the case. Inbound BackTrack may not affect server broadcast at all. **Tier:** supporting, not a primary packet-cheat verdict.

### 9.6 Knockback response

Without a known impulse, do not classify partial velocity. If the server rebroadcasts remote velocity on this protocol/server, save the exact impulse and a calibrated `τ` uncertainty; otherwise restrict to extreme full-cancel candidates after an isolated, known-strength hit. Predict a **set** of post-hit trajectories across plausible pre-hit velocity, input, friction, hit slowdown and collision. Measure minimum residual to that set over 3–5 ticks; exempt walls, stairs/slabs, water/web, ladders, slime, vehicles, explosions, multiple hits, jump resets and teleports. Compare only clean repeated episodes. **Tier:** supporting; strong only if impulse and terrain are known and no legal trajectory fits.

### 9.7 Placement and NoSlow/movement envelopes

First build a block-change attribution record: which players were in range, holding what, support face candidates, swing/use state, timestamps, and plugin-placed possibilities. A scaffold episode is a series of confidently attributed placements while traversing an edge. Compute distance from observed look ray to *any* valid support face across lag/interpolation windows; do not demand an exact cursor Rain cannot see. Compare placement cadence and safe-edge movement with skilled human bridging. For NoSlow, require confirmed use-item state across the movement window and a known movement envelope for surface/effects/sprint/knockback. For Timer/Speed/Flight, require terrain/version profiles and reject teleports/corrections. **Tier:** placement and NoSlow supporting; only blatant motion outside broad legal envelopes may be strong. Raven/NightX fast placement should not be claimed solely from cadence.

### 9.8 Checks explicitly rejected for current Rain

Do **not** implement public detectors for ping spoof, packet Criticals, C0F/transaction Disabler, direct BackTrack mode, raw mouse GCD, exact AutoClicker CPS, camera-vs-server silent rotations, 10% partial Velocity, or ordinary WTap/LegitVelocity. Rain's current observations do not identify these reliably. Keep the research question open if a future authorized server-side plugin or verified observer protocol provides more data; do not imply the passive client can gain serverbound packets by adding a local incoming hook.

## 10. False-positive adversarial audit

Before a detector can raise a public alert, test it against these **legitimate counterexamples**. The table names the mechanism by which each can fool a passive observer and the required response.

| Legitimate condition | Affected detector(s) | Why it resembles a cheat; required gate |
|---|---|---|
| High ping, one-player jitter, packet loss | Reach, lag, rotations, knockback, click timing | Server/observer sees stale or burst updates. Expand history windows conservatively; mark interval missing; abstain if uncertainty eclipses residual. Do not treat entity-local lag as proof. |
| Server TPS drop, batch rebroadcast, observer low FPS | All timing, derivatives, movement | Several remote events collapse into one local tick. Use monotonic arrival and world tick coverage; compare peers/global lag; never count interpolated steps as independent samples. |
| Interpolation, teleport/correction, entity load/unload | Reach, aim, speed, scaffold | Rendered location/angle differs from wire state; gaps mimic bursts. Stamp source and reset/hold episode on discontinuity. |
| Knockback, explosion, collision, stairs/slabs, liquids/webs, ice/slime | Movement, NoSlow, Velocity | Changes speed/trajectory without cheat. Use collision/surface model or abstain. A simple `onGround` flag is insufficient. |
| Potion/equipment effects, enchantments, server movement or PvP plugins | Speed, FastBreak, knockback, reach | Legal envelope changes. Profile server rules or abstain; avoid default-vanilla claims on unknown servers. |
| Skilled aim, flicks, target crossings, sensitivity extremes, high DPI | Aim, switch, GCD | Sharp snaps, low error, overshoot and precise tracking are legitimate. Require repeated contextual deviations; raw GCD impossible from byte-angle stream. |
| Jitter/butterfly clicking, held mining, block breaking relay | Click statistics | Legit high CPS or constant relayed cadence. Exclude mining; use click stats only as supporting after event-quality checks. |
| Multiple overlapping players, projectiles, environmental damage | Reach, aura, knockback, AutoBlock | Incorrectly attributes hurt to suspect. Maintain alternate-attacker graph; abstain when ambiguous. |
| Human eagle/god bridging, team block placement, server block edits | Scaffold, FastPlace | Short crouches, fast placement, apparent off-face blocks. Require actual block-change attribution and valid support geometry; compare skilled builders. |
| Version/protocol translation, creative/spectator abilities, custom combat | All physical checks | Hitbox, range, swing, weapon and block behavior differ. Feature-gate by verified version and game mode; test 1.8.9 separately from later servers. |

**Fail-open does not mean discard data:** keep a non-accusatory transcript with the quality reason. The same legitimate counterexample must be replayed after every threshold, feature, or attribution change. Avoid “fixing” FPs by adding undocumented hardcoded margins; record the measured uncertainty and its source.

## 11. Evidence, confidence, and explanations

### 11.1 Candidate data contract

```text
Observation {uuid, source, clientTick, monotonicTime, world, entityId,
             rawOrInterpolatedPos, yawPitch, stateBits, visibility, qualityTags}
CandidateEpisode {id, type, actorCandidates, victimCandidates, timeInterval,
                  sourceObservationIds, alternativeCauses, missingFields}
Evidence {hypothesis, episodeId, detectorVersion, residual, nullEnvelope,
          reliability, severity, dependencyGroup, exclusionsChecked, explanation}
Decision {state: insufficient | watch | review | highConfidence,
          evidenceIds, contradictions, exposureCount, lastValidObservation}
```

Keep 20–60 seconds of bounded in-memory context around anomalies and optionally export a privacy-aware JSON/CSV transcript with source/version, observations, reconstructed event alternatives, thresholds, and reasons for abstention. An exported clip should permit deterministic replay of **detector math**, not merely a screenshot. Make export user-triggered by default; player identifiers are sensitive and need retention controls.

### 11.2 Fusion without double counting

Let `z_i` be an episode detector's *empirically calibrated* log-likelihood ratio `log(P(feature_i | cheat)/P(feature_i | legit))` **only after** validation. Before that, use ordinal severities, not pseudo-probabilities. For each dependency group `g` within one episode, cap or take the most informative `z_i`, then aggregate across independent episodes with decay and exposure requirements:

`S_t = decay_by_clean_exposure(S_(t−1)) + Σ_g cap_g(max_i∈g reliability_i · z_i)`.

An illustrative **non-calibrated** case: a clean large reach residual scores 4 evidence units; a target snap and low aim error from the *same inferred hit* together are capped at 2; a later independently observed anomalous reach episode adds 4. The internal index becomes 10, but it is **not “90% cheating.”** If the initial hit attribution is ambiguous, all three dependent contributions are suppressed. If a global lag episode appears, pause/invalidates timing-derived evidence rather than adding a contradictory “legit” vote. A deterministic explanation might read: “Two isolated inferred hits exceeded the broad 1.8 reach envelope; nearest legal reconstructed distances were 4.2 and 4.4 blocks; no alternate attacker was visible; both episodes had continuous updates.” It must also state remaining unknowns: server reach rules and suspect-to-server latency.

### 11.3 Baselines: useful only with safeguards

A per-player baseline can normalize each person's ordinary turn magnitude, quantized turn distribution, and fight-vs-nonfight motion. It **cannot** be treated as a trusted human identity: a cheater may be active from first sight, toggle halfway through, or intentionally train the baseline. Build robust distributions only from high-quality, low-ambiguity *noncombat* periods; freeze them during suspected episodes; cap their influence; fall back to population cohorts by version/distance/target speed when exposure is insufficient. Compare combat to matched noncombat **within player**, but do not assume all human combat resembles noncombat. Evaluate leave-player-out and “cheat from session start” cases. Baseline deviation is supporting evidence, never proof.

## 12. Rain dataset design

**Record the deployed observer stream first.** Each row/episode should include schema and detector version, source provenance (tick entity versus packet), anonymized subject/session/server IDs, protocol and game mode, timestamps and gaps, observer FPS/tick health, tab RTT if available (clearly labeled proxy), local world geometry, all nearby player poses/box uncertainty, remote status/swing/hurt/use/held item, block changes, candidate attribution alternatives, features, quality gates, and **reason for missingness**. Store short raw sequences as well as aggregated windows; otherwise a future feature cannot be audited. Controlled ground truth belongs in a separate label manifest: legit/cheat family, source commit/build, exact settings, activation intervals, operator/script, target and environment. Do not put cheat settings, session ID, or server marker into model features.

Collect diverse **legitimate** players: novice to expert, varied sensitivity/DPI/FPS/OS, different mice and accessibility settings, high/low ping with jitter and packet loss, normal/jitter/butterfly clicking where server rules allow, strafing/jumping/combo/bridging, panic flicks, missed hits, crossing/overlapping opponents, item use, potions, water/stairs/slabs/webs/collision, and nonstandard but allowed server mechanics. Label *behaviors and contexts*, not merely “trusted players.” Obtain consent and avoid publishing identifying raw trajectories without review.

Collect controlled **cheat** sessions with Raven/NightX code/configuration families and at least one held-out client, spanning blatant and subtle settings: AimAssist speed/FOV/click-only/pitch, Aura rotation/target mode/fail/CPS/raycast/no-swing, Reach 3.1–6, HitBox size, Velocity 0–100%/chance/conditional, Scaffold/LegitScaffold/AutoBlock modes, Blink/FakeLag timings, timer/speed/flight profiles. Record **negative sessions with module enabled but no activation**. Cheater labels must be time-local; otherwise the model learns idle/chat/menu context. Do not run untrusted binaries as part of this research report; future controlled runs need a separate reviewed test environment.

Split **by player and session**, grouping all overlapping windows and both sides of the same fight. Use a held-out server/protocol slice and, for adversarial generalization, a held-out cheat implementation/configuration. Prevent preprocessing leakage: estimate scalers/feature selection/thresholds only on train, tune on validation, report final test once. Use nested or separate calibration sets. Compare metrics at **episode and player-session alert level**, not just per-window accuracy; 1,000 correlated windows are not 1,000 independent trials. Report FPR with exact denominators and upper confidence bounds across skill, ping, FPS, server and protocol strata. At target FPR 0.1%, roughly 3,000 independent legit sessions with zero flags are needed just to place the simple 95% “rule of three” upper bound near 0.1%; far more are needed for stable subgroup estimates. This is why “95% accuracy” on balanced windows is an inadequate shipping criterion.

## 13. ML feasibility and decision gate

**Stage 0:** deterministic features/quality gates and blind human review of transcripts. **Stage 1:** collect a representative labeled corpus and establish simple baseline models. **Stage 2:** try Random Forest or gradient-boosted trees on episode-level interpretable features (geometry residuals, error reduction, turn variability, timing quality, lag correlation) and calibrate output on held-out players. Trees handle nonlinear interactions and missingness indicators, are fast, and support local feature attribution; they still learn artifacts if sessions leak or quality features encode labels. **Stage 3:** only if tree models clearly fail on matched, sufficiently large sequence data, evaluate 1D CNN/LSTM or temporal transformers with identical splits/abstention policy. Sequence models may capture order and target-switch shape but require more sessions, are harder to calibrate and explain, and can overfit server tick/render artifacts. Any model must beat the deterministic system on a preregistered **false-positive-constrained** metric, including held-out cheats and expert legit players. Otherwise keep it offline.

Use *selective classification*: the model may abstain when input quality or out-of-distribution distance is poor. Calibrate probabilities for the **actual cheat prevalence and observer setup**; a balanced training set changes class priors. Track drift by server/protocol/release; never update weights from self-labeled Rain flags. A model cannot recover hidden clicks or serverbound packets from remote snapshots, no matter how sophisticated its architecture.

## 14. Testing methodology and acceptance criteria

1. **Source-level fixtures:** deterministic traces for entity interpolation, byte-angle wrapping, hurt/swing timing, two possible attackers, desync gaps, world transition, and duplicate/late packet ordering. Assert both positive candidates and explicit abstentions. Tests must exercise the real feature/decision pipeline, not copy its formulas into expectations.
2. **Paired observer capture:** on a controlled server, record server-authoritative events and Rain's observer-only stream for the same scenes. Compare what information survives rebroadcast and interpolation. These server logs are *evaluation oracle only*, not an input to Rain.
3. **False-positive gauntlet:** run the §10 conditions with skilled volunteers and server variants. Include high ping/jitter, low FPS, low TPS, teleport, knockback, stairs/slabs/water/web, potions, target crossing, crowded fights, block plugins, 1.8.9 and translated versions. Record every abstention reason and alert transcript.
4. **Cheat configurations:** future sandboxed, permissioned validation against every source-described subtle and aggressive configuration; include mode enabled but idle, and server rejection/correction. Label actual activation, not module checkbox.
5. **Shadow deployment:** no public flags initially. Review blinded candidate transcripts and estimate per-session false-alert rate, coverage, time to evidence, precision at realistic base rates, and subgroup confidence intervals. Tune only on a designated validation corpus. Freeze thresholds before final test.
6. **Regression:** any detector change reruns prior legitimate counterexamples and held-out cheat families. Verify memory bounds and cleanup on player despawn, world change, and injected runtime enable/disable. A packet tap must be proven read-only and thread-safe in both Forge and injected targets.

Acceptance gate for a public high-confidence label: documented observable prerequisites; reproducible evidence; validated independent-event FPR target (set by Rain's product policy, initially ≤0.1% of legitimate player-sessions overall **and** no uncontrolled subgroup failures); sufficient coverage; no contradictory legal reconstruction; and reviewable examples. A detector that meets a low FPR only by never firing is safe but not useful; report both **coverage** and detection recall at that FPR. Do not widen thresholds to claim coverage on subtle cheats the observer cannot identify.

## 16. Highest-value changes and assumptions to challenge

1. **Replace “flagged Killaura/AutoBlock/LegitScaffold” as a first-hit truth with an evidence state.** Current names overclaim what the checks actually establish. Keep historical behavior separate from new shadow results until validated.
2. **Stop treating `isSwingInProgress` and `hurtTime` as attack packets.** They are animation/state proxies. A single attribution error can currently feed both Killaura and AutoBlock, creating false corroboration.
3. **Do not spend early effort on raw rotation GCD, CPS or packet Disabler signatures.** The necessary upstream information is absent or quantized away. The strongest near-term accuracy gain is reducing incorrect events and exposing uncertainty.
4. **Physically possible envelopes beat isolated thresholds**, but Rain must also admit when it cannot bound the possible set. Grim's methods are valuable only after downsizing them to Rain's information.
5. **Use high-quality negative controls.** Compare a suspect's timing with moving peers, and combat turns with matched noncombat turns, without pretending those controls are proof. Keep server-specific behavior visible in the explanation.
6. **Make abstention an explicit product outcome.** For subtle Raven AimAssist or 3.1–3.3 reach, “insufficient evidence” will often be the technically correct answer. A detector promising universal coverage would be less credible than one with measured blind spots.

## 17. Open research questions

* Which exact server-to-observer packets survive Rain's 1.8.9 Forge and Badlion/injected environments, and do translations alter entity look, animation, damage or velocity semantics?
* How often can a remote swing + hurt be uniquely attributed on real PvP servers? What fraction of fights is usable for reach/aim after honest quality gates?
* What latency/interpolation envelope does a two-observer plus server-oracle experiment measure for stationary versus sprinting/dashing combat? Does any margin allow useful detection of 3.3-block reach at acceptably low FPR? The working hypothesis is **probably not** for most fights.
* Do typical 1.8 servers broadcast other-player velocity impulses? If not, is knockback ever more than weak supporting evidence? Are server-specific KB rules discoverable without privileged integration?
* Can actual placed blocks be attributed confidently enough to compute a support-face aim envelope, or should Rain drop Scaffold as an accusation altogether?
* Are Raven's Backtrack and various NightX bypass modes functional on the intended servers? Static intent alone does not establish runtime effectiveness; future testing must measure the accepted server behavior, not assume it.
* Is an optional server plugin, trusted replay or controlled data-collection companion acceptable to the product? That would answer a **different** architecture question; any resulting server-informed detector must be labeled separately from passive Rain.
* What is Rain's acceptable per-player-session false-alert budget, and how should public nametags represent “review” versus high-confidence evidence? This is a product decision requiring empirical validation.
